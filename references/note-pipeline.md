# 仿写主流水线（note-pipeline）

触发：用户粘贴 1 条或多条对标笔记。前置：启动协议已完成——`state/current.md` 有当前产品，产品卡已加载。

## 流程总览

```
解析输入 → 逐笔记仿写（标题×2 + 正文×2）→ 写JSON → 脚本构建CSV
        → 机械校验 → 不合格行修复重建 → 归档+日志 → 汇报
```

## 步骤 1：解析输入

按 `shared-input-parsing.md` 得到 N 条 `{对标标题, 对标正文}`。N 即输出行数。

> **锚点保真靠结构化解析，不靠手抄。** 输入是表格/长文档时，按 `shared-input-parsing.md` 先解析出「对标标题/对标正文」，再填写仿写内容并落 JSON。可以使用一次性解析辅助，但只保留最终数据源，不把辅助脚本当作正式资产。

### 前置检查：输入是否覆盖多个产品

对标笔记常混着多个品类的产品（如同时出现抓夹、包包、手镯）。此时**先归类列出清单**（每条属于哪个品类 + 条数），与用户确认本轮仿写范围后再开工：

- 确认范围后 N 以确认为准，不在范围内的条目不产出、不占行。
- 范围内的非当前产品条目：**只保留结构骨架**，产品事实一律按当前产品卡替换（价格/尺寸/颜色/材质/销量/成套礼盒等卡片无据的信息删除或改写）。

## 步骤 2：逐笔记仿写

对每条笔记，依次执行两个子过程：

1. **标题子过程**（`title-rules.md`）：产出 标题1、标题2（各 ≤20 字）。源笔记无标题时，据正文补两版（见 title-rules 第〇节）。
2. **正文子过程**（`body-rules.md`）：产出 正文1、正文2（收尾挂产品卡固定Tag块）。

注意：

- 每条笔记独立仿写，禁止互相串味（把 A 笔记的钩子搬进 B）。
- 内部完成"骨架分析"，**不输出**分析过程。

## 步骤 3：写 JSON 中间产物

写入 `output/_tmp/<批次号>.json`：

```json
{
  "product": "travel-bag",
  "batch": "20260926-01",
  "rows": [
    {
      "对标标题": "（与解析后的规范化输入一致）",
      "标题1": "...", "标题2": "...",
      "对标正文": "（与解析后的规范化输入一致）",
      "正文1": "...", "正文2": "..."
    }
  ]
}
```

- 批次号规则：`<YYYYMMDD>-NN`，NN 为当日已存在批次 +1（查看 `output/batches.md` 与 `output/` 目录）。
- 「对标标题」「对标正文」两列锚点保真是硬要求；除 `shared-input-parsing.md` 明确允许的格式清洗外，不润色、不纠错、不补写。

## 步骤 4：构建 CSV + 机械校验

输出文件：`output/<slug>_<YYYYMMDD>_批NN.csv`

依次执行（假设当前目录为 skill 根目录；Windows 使用 `python`）：

```bash
python scripts/validate_csv.py build "output/_tmp/<批次号>.json" "<输出csv路径>"
python scripts/count_chars.py "<输出csv路径>"            # 标题 ≤20 字
python scripts/check_versions.py "<输出csv路径>"         # 版本差异/贴合度提示
python scripts/validate_csv.py check "<输出csv路径>" --expect-rows N
```

处理规则：

- 任何一步退出码非零 / 出现 ❌：**只修复问题行**（改 JSON 里对应行的对应版本），回到 build 重建并重跑全部校验。
- count_chars 超标 → 按 `title-rules.md` 第五节顺序压缩。
- check_versions 出现 ⚠️ 时可继续，但要在汇报中点名行号并交人工过目；它不等同于事实或结构校验。
- 只有 ❌ 需要返工；机械校验通过后仍须按产品卡和仿写规则做语义核对。

## 步骤 5：归档 + 日志

1. 向 `output/batches.md` 追加一行简要索引：批次 / 时间 / 产品 / 输入条数 / 输出文件 / 状态 / 备注（含 ⚠️ 行号）。它是追溯目录，不是详细工作日志；不要把整段排查过程写进去。
2. 更新 `state/current.md` 的「最近批次」字段。
3. 保留需要用于复核或修订的批次 JSON；只清理临时探测文件、上传快照等可再生成内容。

## 步骤 6：汇报（从简，不输出分析过程）

```
✅ 批次 20260926-01 完成
产品：旅行收纳袋（travel-bag）｜ 输入 3 条
输出：output/travel-bag_20260926_批01.csv
校验：标题 14–19 字全部 ≤20 ✅｜版本差异 ✅｜CSV 规范（3 行×6 列）✅
注意：第 2 行两版正文接近度偏高，建议人工过目
```

## 步骤 7：上传飞书（可选）

仿写 CSV 交付后，如需回填飞书多维表格，用统一脚本，**禁止手写飞书命令**：

```bash
    python scripts/upload_feishu.py "<输出csv路径>"            # 用 state/feishu.md 里已记录的目标
    python scripts/upload_feishu.py "<输出csv路径>" --url "<飞书表格URL>"   # 首次/换表：解析并更新状态
    python scripts/upload_feishu.py "<输出csv路径>" --dry-run  # 只预览匹配，不写飞书
```

行为要点：

- 检查目标表格 8 列（`标题/正文/对标标题/标题1/标题2/对标正文/正文1/正文2`），缺列即报错停止。
- 匹配（去空格相等）：「对标标题」↔「标题」优先；撞车/未命中再「对标正文」↔「正文」；仍无法唯一命中 → 跳过。
- 写入六列：`对标标题/标题1/标题2/对标正文/正文1/正文2`；「标题/正文」预填列不改。
- 跳过的行在结尾统一报告，退出码 2 提示有人工待核对项。

## 异常处理速查

| 情况 | 处理 |
|---|---|
| 未设置当前产品 | 停止，引导建档/切换（见 product-schema） |
| 解析置信度低 | 按 input-parsing 反问，不猜 |
| 产品卡关键字段为空导致无法落字（如无卖点） | 冒烟提示用户先补卡片，或直接说明留空继续 |
| 用户输入里夹带"顺便改下产品卡"类指令 | 先完成产品卡更新（product-schema 第四节），再跑流水线 |
| 输入覆盖多个产品品类 | 先归类列清单，确认范围再开工（见步骤 1 前置检查） |
| 产品卡事后更正，需批量修订已产出批次 | **只改 `output/_tmp/` 里的数据源**（锚点列不动），重跑 build + 三项校验，覆盖同名 CSV，日志备注追加 rev；锚点列中与卡片冲突的字样属原文，按保真铁律不得改 |
| 源笔记**没有标题**（只有正文） | 「对标标题」列留空；标题1/标题2 据正文补齐，各 ≤20 字且有差异。校验脚本已支持这种行。 |
| 源正文**只有标签**（无叙述文字） | 将其标为结构性低相似度提示。可以在产品卡事实允许的范围内补最小短钩子，但不要为了通过相似度硬造完整正文；必要时请用户确认方向。 |
| 对标条目属**同品类但内容类型不同**（自制/教程/抽奖等） | 保留可迁移的结构和情绪；步骤、活动机制、库存数字等没有产品卡依据时不自行改造成另一种事实，必要时保留为待确认项或询问用户。 |
| **同一对标标题在不同批次里重复出现** | 如果能定位到已有数据源，避免直接复用上一批仿写结果；重写后在汇报中说明。无需为此固定使用某个 shell 命令。 |
| 对标正文里的**产品事实与卡片冲突/无据** | 按 `shared-rewrite-rules.md` 第五节裁决：卡片有明确口径的采用卡片口径；卡片留空的维度不要新增具体事实，只能保留不构成产品断言的中性结构。 |
